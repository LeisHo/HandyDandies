ARCHITECTURE

Inside `main.js`, in roughly this order:

1. **Dev panel** (`DEV_GROUPS`, `initDevPanel()`) -- Field Layout (rows,
   columns, ROW spacing and COLUMN spacing as 2 independent sliders, hand
   scale, Alternate/Progressive row-offset controls + a mode-switch
   checkbox), Cursor Tracking, Camera (X/Y/Z position + FOV only -- see #2),
   Lighting (full parity with HANDO's own group, including Key Light Aim
   Height), Toon Shading (steps/threshold/floor/ceiling/base tint/texture
   influence/tint/rim intensity-power-color -- ported from HANDO), Outline
   (enabled/use-pass/color/hull-thickness/pass thickness-strength-glow --
   ported from HANDO), Background, Debug (grid helper, wireframe).
   `initDevPanel()`'s onChange callbacks are detached and reattached around
   the init call itself (see GOTCHAS).
2. **Camera: pan + zoom only, no orbit** -- `OrbitControls` with
   `enableRotate: false`, `mouseButtons: { LEFT: PAN, MIDDLE: DOLLY, RIGHT:
   PAN }`, `touches: { ONE: PAN, TWO: DOLLY_PAN }` (gives mobile one-finger-
   drag-pan/two-finger-pinch-zoom for free -- no custom touch code). Camera
   X/Y/Z/FOV/Zoom dev-panel sliders all DRIVE the camera (`applyCameraControl()`)
   and are kept in sync FROM the live camera every frame
   (`syncCameraPanelFromLive()`, using the imported `syncValue()` -- it
   skips a row currently focused, so this never fights a live slider edit).
   `cameraZoom` specifically reads/writes `camera.position.distanceTo(
   controls.target)` via `setCameraDistance()` (moves the camera along its
   existing camera-to-target line, leaving `controls.target` untouched) --
   the exact same axis OrbitControls' own scroll/pinch dolly already moves
   the camera along, so the slider and a scroll tick are indistinguishable
   to anything reading `camera.position` afterward. Ported from HANDO's own
   2-way Camera-group pattern, simplified (no Yaw/Pitch, since a
   non-orbiting camera has no "look direction" concept to expose).
3. **Camera/lighting/target-plane framing is frozen after the FIRST build**
   (`framedOnce` flag in `rebuildField()`) -- direct request ("Field layout
   shouldn't affect view scale"). Rows/columns/spacing/offset changes only
   ever touch `relayoutField()` (hand positions/scale), never camera or
   `sceneState.fieldRadius` again after the first build.
4. **Cursor -> 3D target** (`cursorNDC`, `updateCursorTarget()`) -- a
   `window` `pointermove` listener updates `cursorNDC`; each frame, a
   `THREE.Raycaster` casts from the camera through `cursorNDC` and
   intersects a `THREE.Plane` (`targetPlane`) positioned in front of the
   hand field, at a depth of `fieldRadius * cfg.targetDepthFactor` (frozen
   per #3). A REAL 3D point with a depth offset from the hands' own z=0
   plane -- critical for the requested pitch/reveal effect.
5. **Model loading + bind-pose measurement** (the `GLTFLoader().load(...)`
   callback) -- finds the skinned mesh, hides stray meshes, measures the
   bind-pose "pointing" direction (bone `rHand` -> bone `rMid3`, world
   space, root at identity transform at this point). `alignQuat` rotates
   that direction onto local -Z; `handLengthRaw` is its measured length
   (used for both auto-scaling AND the outline hull-thickness reference,
   replacing HANDO's own bounding-radius reference since each hand instance
   is its own separately-scaled object here). Also builds the ONE shared
   `toonMaterial` here (`createToonMaterial(skinned.material.map)`).
   Same block also measures `palmFaceCorrectionQuat` (Cursor Tracking's
   own "Palm Faces Cursor" checkbox, see GOTCHAS) -- the bind-pose palm-
   plane normal (`(pinky-base - wrist) x (index-base - wrist)`, bones
   `rPinky1`/`rIndex1`/`rHand`), rotated onto local -Z the same way
   `pointDir` is, so it can be composed onto the live lookAt quaternion
   as a fixed correction when that mode is on.
6. **Field layout** (`rebuildField()`, `relayoutField()`,
   `computeBaseScale()`) -- `rebuildField()` clears and recreates every hand
   instance: `cloneSkeletal(modelRoot)` (three.js `SkeletonUtils.clone`,
   imported as `{ clone as cloneSkeletal }` -- see GOTCHAS), `clone`'s own
   skinned mesh gets its own `.material = toonMaterial.clone()` (own
   `clippingPlanes`/`onBeforeCompile`, corrected from an earlier shared-
   material design -- see GOTCHAS), plus its own `outlineMesh`
   (`buildOutlineMesh()`, a `sourceMesh.clone()` sharing that hand's own
   skeleton, using its own cloned `outlineMaterial` too) parented under
   `clone` so it inherits the bind-pose `alignQuat` automatically. `relayoutField()` (cheaper --
   repositions/rescales only) lays out a centered grid using INDEPENDENT
   `cfg.rowSpacing`/`cfg.columnSpacing`, applying a per-row X offset: in
   Alternate mode, odd rows shift by a fixed `cfg.alternateRowOffset`; in
   Progressive mode, row `r` shifts by `r * cfg.progressiveRowOffset`
   (mutually exclusive via `cfg.useProgressiveOffset`).
   `computeBaseScale()` uses a FIXED reference length
   (`HAND_SCALE_REFERENCE_LENGTH = 8`, chosen to match this project's own
   original spacing defaults so existing settings don't visually jump) --
   per direct request, hand scale and grid spacing are fully independent:
   dragging Row Spacing or Column Spacing only repositions hands via
   `relayoutField()`, never rescales them; only `cfg.handScale` does that.
   (An earlier version derived the scale reference from `Math.min(
   rowSpacing, columnSpacing)`, so dragging either spacing slider silently
   changed hand size too -- confirmed removed directly: forcing Row
   Spacing 10->30 and Column Spacing 11.5->2 left `computeBaseScale()`'s
   result numerically unchanged, while the Hand Scale slider still visibly
   changes it.)
7. **Toon material + outline** -- `createToonMaterial()`/
   `makeGradientTexture()`/`rebuildGradientMap()` and the outline
   `ShaderMaterial` + inverted-hull shaders are ported from HANDO. Each
   field hand gets its own `.clone()` of both materials (own
   `clippingPlanes`, for Hide Wrist/Arm Length -- see GOTCHAS for why a
   shared material broke this); the single Pose Preview hand uses the
   template materials directly. `forEachToonMaterial()`/
   `forEachOutlineMaterial()` keep every existing "change a shared
   material setting" dev-panel control (base tint, wireframe, outline
   color/thickness, gradient rebuild) working across all the per-hand
   clones plus the template.
   Both materials run with `depthTest: true` (the default) -- see #9 below
   for the depth-buffer-per-hand technique that makes cross-hand render
   ordering work without needing to disable it. `updateOutlineVisibility()`
   toggles between the 2
   outline techniques: hull-mesh `.visible` per instance, or a single
   `OutlinePass` with `selectedObjects` set to every hand's own skinned
   mesh at once (cheaper for many instances than N extra hull meshes,
   though both are implemented and dev-panel toggleable, matching HANDO's
   own choice; both default OFF currently).
8. **Render loop** (`animate()`) -- self-heals renderer/composer size every
   frame (see GOTCHAS' `window.innerWidth` entry) before `controls.update()`,
   `syncCameraPanelFromLive()`, the cursor-target recompute, the per-hand
   look-at slerp (via `new THREE.Matrix4().lookAt(...)`, not
   `Object3D.lookAt()` -- see below), the per-hand render-order assignment
   (#9), and finally `composer.render()` (RenderPass -> OutlinePass ->
   OutputPass) instead of a plain `renderer.render()`, now that
   post-processing exists.
9. **Cursor-distance render ordering** (`updateRenderOrder()`) -- per direct
   request, hands FURTHEST from the cursor target render on top of nearer
   ones, not whichever is actually closer to the camera. Each hand's
   `effectiveRenderOrder` (persisted on the hand object, not recomputed
   from scratch every frame) normally tracks its own live
   `wrapper.position.distanceTo(cursorTarget)`; `skinnedMesh.renderOrder`
   reads that value directly, `outlineMesh.renderOrder` reads it minus a
   small epsilon so a hand's own outline always draws just before (under)
   its own fill. This has a visual effect despite both materials keeping
   `depthTest: true` (#7) because each hand's fill AND outline mesh also
   get an `onBeforeRender = (r) => r.clearDepth()` hook (attached in
   `rebuildField()`) -- clearing the depth buffer immediately before that
   hand's own draw call means a hand's own triangles still depth-test
   correctly against EACH OTHER (real self-occlusion), while stacking
   BETWEEN hands is decided purely by draw order (`renderOrder`) since
   each hand starts from a fresh depth buffer and therefore always wins
   the draw over whatever was rendered immediately before it. An earlier
   version of this project used `depthTest: false` directly instead (no
   per-hand depth clear) -- simpler, but broke self-occlusion WITHIN a
   single hand's own geometry (see GOTCHAS for the real bug this caused
   and how it was found/fixed). See GOTCHAS for the residual tradeoff the
   current technique still has.
10. **"Prevent Reordering Flash"** (`cfg.preventReorderFlash`, Debug group,
    `REORDER_SMOOTHING` constant) -- when on, `updateRenderOrder()`
    approximates every hand's on-screen footprint as a circle, using the
    mesh's own MEASURED bounding sphere (`handBoundsCenterLocal`/
    `handBoundsRadiusLocal`, computed once at load via `THREE.Box3` +
    `.getBoundingSphere()` on the original skinned mesh, in the same
    identity-transform frame `alignQuat`/`handLengthRaw` are measured in)
    -- NOT `wrapper.position` and NOT a radius derived from the wrist-to-
    fingertip bone distance (see GOTCHAS for why that undersized/mis-
    centered version was a real, reported bug). Each frame, the sphere's
    LOCAL center is put through this hand's actual transform chain (scale
    -> `alignQuat` -> live `wrapper.quaternion` -> `wrapper.position`) --
    a sphere's radius only needs scaling, not rotating -- then projected
    to screen pixels via standard perspective scaling: `pxPerWorldUnit =
    canvasHeight / (2 * tan(vFov/2) * distanceToCamera)`. An O(n^2)
    pairwise check then flags `hand.isOverlapping` for any
    hand currently touching another on screen. A hand that ISN'T
    overlapping anything just snaps straight to its own live cursor
    distance (no lag, fully responsive); a hand that IS overlapping
    something blends toward its live distance instead of snapping
    (`effectiveRenderOrder += (live - effectiveRenderOrder) *
    REORDER_SMOOTHING`, an exponential lerp, `REORDER_SMOOTHING = 0.15`).
    Nothing is ever derived from ANOTHER hand's value -- every hand's own
    order is always purely a function of its OWN live distance (blended or
    not), which is what makes this version structurally immune to both
    failure modes below.
    **This is the 3rd design for this feature -- the first 2 are kept in
    the function's own comment as a measured cautionary tale.** v1 froze a
    hand's ENTIRE order the instant it overlapped ANYTHING, not resuming
    until every overlap cleared -- in a dense/zoomed-in view where most
    hands are always touching some neighbor, no hand ever got a single
    overlap-free frame to unfreeze on, so the WHOLE FIELD froze solid
    PERMANENTLY the moment the checkbox was turned on (confirmed: a
    240-frame simulated sweep at closer zoom showed all 510 hands frozen,
    0 updates for the entire run). v2/v3 tried a per-PAIR lock instead
    (remembering which of 2 overlapping hands should stay on top, nudging
    or unconditionally pinning the other to `partner + epsilon`) -- v3's
    unconditional pin seemed to fix v2's own instability, but in a dense
    field, chains of simultaneous locks (A-under-B-under-C-under-D...)
    compound: every hand in a long chain collapses toward whichever hand
    anchors that chain, discarding real distances almost entirely.
    Measured directly: sampling ~87,000 random pairs whose TRUE distances
    differed by more than 15 world units (a large, unambiguous gap), 21%
    STILL rendered in the wrong relative order under v3 -- worse than no
    fix at all, and exactly the reported regression ("certain hands render
    above a hand further from the cursor" + "flashing... worse than
    before"). The current smoothing design was measured against the same
    87,000-pair test at under 0.1% wrong-order rate, 0 stuck hands across
    150 simulated frames, and roughly half the frame-to-frame flip rate
    (among hands ACTUALLY overlapping on screen) compared to no fix at
    all. Trade-off, disclosed: this is no longer a literal hard freeze
    ("won't change until they clear") -- it's a fast blend that mostly
    prevents instant pops without the 2 failure modes a literal freeze/pin
    kept producing at this field's actual density.
    **A DEEPER, STRUCTURAL limitation surfaced after this design was
    already shipping and the overlap geometry was separately fixed (see
    GOTCHAS): smoothing the NUMBER does not and CANNOT smooth the VISUAL
    SWAP.** `renderOrder` is a discrete sort key -- a hand is drawn
    strictly before or after another, with no partial/blended state in
    between (this whole feature exists because `depthTest:false` removes
    the GPU's own continuous, per-pixel depth resolution). Traced a real
    flip frame-by-frame: the gap between 2 overlapping hands' smoothed
    values shrank perfectly cleanly and monotonically every single frame
    (-1.24 -> -0.92 -> -0.58 -> -0.23 -> +0.11 -> +0.43, zero discontinuity
    anywhere) -- yet the instant that gap crossed zero, the actual draw
    order (and therefore the visible stacking) flipped completely, in one
    frame, same as it would with NO smoothing applied at all. Smoothing
    demonstrably still helps (see the measured wrong-order/flip-rate
    numbers above) by damping NOISE-driven back-and-forth crossings and by
    correcting a hand's numeric order to actually match true distance --
    but it cannot make a GENUINE crossing (the cursor's movement actually
    causing 2 hands' true relative order to swap) look like anything other
    than a hard, instant pop, because the render mechanism has no
    continuous transition to interpolate through. Eliminating that
    specific residual pop would need a fundamentally different technique
    (e.g. a real alpha cross-fade between the 2 competing hands during the
    crossing window, which conflicts with the current opaque/
    `depthTest:false` approach and hasn't been attempted) -- a materially
    bigger change than anything else in this feature's history, flagged to
    the user as a scope/architecture decision rather than attempted
    unilaterally.

11. **Pose** (Pose dev-panel group) -- ported from HANDO's own identical
    group (same rig/bone names, same `Hand2.glb` asset): 25 finger sliders
    (Curl/Splay/2nd-Segment-Splay/Curl-Bias/Tip-Twist x5 fingers),
    Wrist Bend/Splay, Whole-Hand Rotation X/Y/Z, and Hide Wrist. Applies
    IDENTICALLY to every hand for now, per direct request -- there is no
    per-hand pose override yet. `boneRestQuat` (captured once, from the
    ORIGINAL un-cloned skeleton's bind pose, right after load and BEFORE
    `rebuildField()` ever clones it) is shared across every hand's own
    distinct skeleton clone, unlike HANDO's per-model `restQuatMap` (which
    only exists there to support 2 DIFFERENT model files with slightly
    different rest poses -- not a factor here, one GLB cloned N times).
    `applyCurl(fingerName)`/`applyWristPose()` loop over every hand in
    `hands`, calling the same `applyCurlToSkeleton()`/
    `applyWristPoseToSkeleton()` HANDO itself uses (ported near-verbatim,
    including all of HANDO's own live-measured per-finger axis/sign/
    magnitude tables) against that hand's own skeleton.

    **A real bug, found and fixed this round, that HANDO's own identical
    code never had to deal with:** HANDO's finger-curl axes are pre-
    rotated by `modelRoot.quaternion` (its own single whole-hand
    orientation) so a "world" curl axis stays anatomically fixed
    regardless of how the hand is posed -- but HANDO has no OTHER rotation
    layer on top of that. This project's own hands have one:
    `wrapper.quaternion`, the per-hand, per-frame cursor-tracking look-at
    (see `animate()`). Confirmed directly, live: with the SAME slider
    values, 2 different hands (facing 2 different directions at that
    moment) produced 2 DIFFERENT local bone quaternions for the identical
    finger -- proof the curl axis was leaking each hand's own CURRENT
    cursor-facing direction into what should be a purely anatomical
    (pose-only) rotation. Fixed by extending `rotateOnTrueWorldAxis()`
    with an optional `excludeQuat` parameter (that hand's own
    `wrapper.quaternion`) factored out of the bone's world quaternion
    before the axis conversion -- the algebra shows `wrapper` and the
    pre-rotation by `cloneBaseQuat` (below) cancel exactly, leaving the
    axis fixed relative to the mesh's own raw/bind-pose frame regardless
    of EITHER rotation. Re-verified after the fix: the same 2-hands test
    now produces byte-identical local bone quaternions. Tip Twist's own
    axis (computed live from 2 bones' actual current positions, not a
    fixed WORLD_X/Y/Z constant) does NOT get this treatment -- it's
    already a true world-space direction and excluding anything from it
    would be wrong.

    **Whole-Hand Rotation X/Y/Z (`updateCloneBaseQuat()`)** -- changes
    `cloneBaseQuat` only, applied to every hand's own `clone.quaternion`
    every frame alongside the Arm Length position update (#12 below).
    `cloneBaseQuat = alignQuat * wholeHandRotQuat` is identical for every
    hand -- only needs recomputing when a Whole-Hand Rotation slider
    actually changes, never `wrapper`'s own transform (the per-frame
    cursor look-at owns that exclusively). See GOTCHAS for a real,
    measured trade-off between Hide Wrist's own grid-alignment requirement
    and HANDO's own palm-center rotation pivot.
12. **Arm Length / Hide Wrist, made reactive** (direct follow-up request:
    "make the crop or arm length dependent on distance from the cursor, so
    the closer it is the shorter the arm length") -- what was a single
    slider-triggered, shared-across-all-hands calculation is now PER-HAND,
    PER-FRAME (`applyHandArmLength()`, called from `updateRenderOrder()`'s
    own existing per-hand loop, reusing the live cursor-distance value that
    loop already computes for render ordering -- no separate distance calc
    needed). `computeArmLengthT(hand, distanceToCursor)` returns this
    hand's current crop fraction: reactive OFF returns `cfg.hideWrist/100`
    (renamed "Default Arm Length" in the panel, unchanged behavior from
    before this round); reactive ON maps the hand's live cursor distance
    (normalized against `sceneState.fieldRadius * ARM_LENGTH_DISTANCE_NORM`
    -- a judgment call, not a derived constant, documented as such in the
    code) through `armLengthCurveParsed` (a user-edited piecewise-linear
    curve, X=normalized distance, Y=raw crop fraction) into
    `armLengthRangeParsed`'s [min,max] bounds. The underlying math
    (`applyHandArmLength()`) is otherwise identical to the original
    single-hideT version -- same cut-point-lands-exactly-on-the-grid-point
    derivation, just parameterized by a value that can now differ per hand
    and per frame instead of being one shared constant.

    **2 new dev-panel widgets that are NOT devPanel.js control types** --
    Min/Max Arm Length (a 2-handle range bar) and Length Scaling Curve (a
    draggable-point curve editor, piecewise-linear, X=distance/Y=crop).
    Neither UI shape exists in the shared, reused-verbatim `devpanel.js`
    engine, and per this project's own convention ("do not fork it, add
    controls via main.js's own DEV_GROUPS instead") neither was added
    there. Both are registered as plain `type:'text'` controls (`cfg[key]`
    holds a JSON string, e.g. `{"min":30,"max":90}` or
    `[{"x":0,"y":1},{"x":1,"y":0}]`) with their OWN custom DOM/SVG and
    pointer-drag handling laid on top of that control's own (hidden)
    generic text input by `buildArmLengthWidgets()`, called once right
    after `initDevPanel()`. Interacting with either widget calls
    `commitTextControl()`, which sets the hidden input's `.value` and
    dispatches a real `'input'` event -- routing through devPanel.js's own
    existing `commit()`/localStorage-save machinery exactly as if the user
    had typed into a plain text box, so Copy/Save/Reset all keep working
    without either widget knowing anything about devPanel.js internals.
    `cfg.armLengthRange`/`cfg.armLengthCurve` (JSON strings) are parsed
    once into `armLengthRangeParsed`/`armLengthCurveParsed` (cached,
    module-level) by `parseArmLengthConfig()` -- called from each control's
    own `onChange` and once right after `initDevPanel()` -- rather than
    re-parsed 510 times a frame inside `computeArmLengthT()`. See GOTCHAS
    for a real TDZ crash this caching introduced (and where these 3 cached
    vars actually had to live to avoid it) and for why devPanel.js's own
    Reset/Copy-restore path needed a small per-frame resync poll
    (`armLengthWidgetResyncs`, polled once per frame from `animate()`)
    since it writes the hidden input's value directly without firing an
    `'input'` event either widget could otherwise just listen for.

Data flow: cursor position -> NDC -> raycast against a plane in front of
the field -> `cursorTarget` (world point) -> per-hand look-at quaternion ->
slerp toward `wrapper.quaternion` -> render. The model's own bind-pose
alignment (`alignQuat`), per-hand grid position/scale, and camera/lighting
framing are all set once (at load / on their own specific control's
change) and never revisited by an unrelated control's change.

GOTCHAS

- **FIXED (was previously misdiagnosed twice -- see CHANGELOG.txt for the
  full 3-round account).** Fine, noisy-looking surface detail in the
  toon-shaded gray/shadow areas (reported directly, with a screenshot) was
  real `depthTest:false` self-occlusion bleed-through, exactly as the user
  described once asked directly: "I can somewhat see through the hand
  itself and the noise represents the obscured surfaces behind the
  frontmost surface." Two earlier theories in this same entry (real mesh
  geometry revealed by grazing light; this project's zero-ambient/full-
  contrast toon recipe vs. HANDO's softer one) were both directly
  disproven by the user, who confirmed HANDO shows no such noise even at
  `ambientIntensity:0`/`toonSteps:2` (matching this project's own
  defaults) across many different hand poses -- ruling out both lighting
  recipe and asset geometry as the cause. Root cause, confirmed by a
  targeted pixel-diff (not a coarse whole-canvas histogram, which is why
  an earlier pass in this same investigation wrongly looked like only an
  8% effect): isolated a single hand in its bind pose, where a finger
  genuinely overlaps the palm in screen space, and diffed every pixel in
  that overlap region between `depthTest:true` and `depthTest:false`.
  8.2% of pixels differed, spatially clustered exactly on the overlap --
  with `depthTest:false`, those pixels rendered as bright/lit (255) where
  `depthTest:true` correctly rendered them as shadowed (132): a wrongly-
  drawn, differently-lit BACK surface was bleeding through the front
  surface, because `depthTest:false` (needed so cursor-distance render
  order works BETWEEN different hands) also disables the GPU's depth test
  WITHIN a single hand's own triangles, leaving self-occlusion to whatever
  order the GPU happens to submit that hand's own triangles in -- which is
  neither guaranteed nor correct. HANDO uses real `depthTest:true`, so its
  self-occlusion is always correct regardless of pose.

  **Fix implemented** (see `createToonMaterial()`, `ensureOutlineMaterial()`,
  and the `onBeforeRender` hooks in `rebuildField()`): both hand materials
  are back to `depthTest:true` (the default), restoring correct self-
  occlusion. Cross-hand stacking (farthest-from-cursor draws on top) is
  now achieved differently: each hand's own fill mesh AND outline mesh get
  an `onBeforeRender = (renderer) => renderer.clearDepth()` hook, wiping
  the depth buffer immediately before that hand's own draw call. This
  means a hand's own triangles are correctly depth-tested against EACH
  OTHER (self-occlusion fixed), while stacking BETWEEN hands is still
  decided purely by draw order (`renderOrder`, unchanged, still set every
  frame from cursor distance in `updateRenderOrder()`) rather than real
  camera depth -- a hand drawn later always wins the overlap against a
  hand drawn earlier, exactly reproducing the old `depthTest:false`
  cross-hand behavior without its self-occlusion side effect.

  Verified directly, live: (1) the same finger-over-palm region that
  showed an 8.2% bleed-through split (132 vs 255) now reads a single
  clean luminance value (132) across all sampled pixels -- self-occlusion
  confirmed fixed; (2) positioned 2 isolated hands at the SAME screen
  position but 60 world units apart in real camera depth, gave the
  PHYSICALLY FARTHER one the HIGHER `renderOrder` and a `MeshBasicMaterial`
  red tint (to remove any ambiguity from the shared toon shader's own
  tint-uniform machinery) -- confirmed the farther-but-later-drawn hand
  visually wins 100% of the sampled overlap pixels despite being 60 units
  further from camera, proving cross-hand render-order stacking still
  works correctly under the new technique; (3) confirmed zero console
  errors on a fresh reload and that `renderOrder` still correlates
  perfectly with cursor distance across all 510 hands (0 inversions across
  509 sorted pairs). One known trade-off, same category as an existing
  documented one: if two hands' `renderOrder` values land extremely close
  together (the near-tie case "Prevent Reordering Flash" already exists to
  soften), their draw sequence could in principle interleave in a way that
  briefly disrupts the per-hand depth-clear grouping -- a minor, transient
  edge case, not a new class of bug, and not separately reproduced.
- **FIXED — real "arms disappearing" bug, present since Hide Wrist/Arm
  Length shipped, MISDIAGNOSED twice as perspective foreshortening before
  being root-caused (see CHANGELOG.txt for the full account, including the
  2 earlier "not a bug" reports this corrects).** User pushed back
  directly ("bro. dont you see in the video arms dissappearing
  completely?"), then gave the decisive clue once asked to point at a
  specific moment: "the dissappearng happens when my mouse is very far
  from the grid... furthest hands should be pointing at the cursor. so

- **"Palm Faces Cursor" (Cursor Tracking group, new checkbox) -- whole-
  object rotation only, deliberately NOT a pose/skeleton feature.**
  Direct request, with an explicit correction mid-task when an
  investigation step looked pose-adjacent ("you shouldnt be doing any
  posing work" / "when i say rotate the hand... I just meant rotate the
  entire model"). Default (fingers point at cursor) already works by
  rotating each hand's WRAPPER so its `alignQuat`-aligned local -Z (the
  bind-pose wrist->middle-fingertip direction) faces the cursor via
  `THREE.Matrix4.lookAt()`; this feature needed the PALM-NORMAL direction
  to be the one aimed at the cursor instead, without touching that
  existing per-frame lookAt code's own shape or any bone/curl value.

  Measured the palm-plane normal the same way `pointDir`/`alignQuat`
  already are (bind-pose bone world positions, identity-transform frame,
  at model-load time): `(pinkyBase - wrist) x (indexBase - wrist)`,

  possible cross-product orders points OUT of the palm vs. into the back
  of the hand) was CALIBRATED LIVE rather than assumed: transformed each
  candidate direction through `alignQuat` and a real hand's own current

  confirming it's the outward palm normal.

  parallel code path: `palmFaceCorrectionQuat = Quaternion.setFromUnitVectors(
  palmNormalRaw.applyQuaternion(alignQuat), (0,0,-1))` -- a FIXED, one-
  time-computed correction (same block as `alignQuat` itself, at model
  load). Given `Q_lookAt.apply((0,0,-1)) == dirToCursor` (lookAt's own
  guarantee) and `R = Quaternion.setFromUnitVectors(v, (0,0,-1))` implies
