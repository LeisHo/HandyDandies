1 request: a "Reordering Flash" checkbox so 2 overlapping hands' cursor-

Added:
- `preventReorderFlash` checkbox (Debug group). When on,
  `updateRenderOrder()` approximates every hand's on-screen footprint as a
  circle (world radius = half the measured hand length x its own scale,
  projected to screen pixels via standard perspective scaling) and runs an
  O(n^2) pairwise screen-space overlap check across all hands. A hand's
  `effectiveRenderOrder` (now a persisted field, not recomputed from
  scratch every frame) only updates from its live cursor-distance when it
  is NOT currently overlapping anything -- while overlapping, it keeps its
  prior order, so 2 fighting hands can't flip mid-overlap; it only
  re-evaluates once that hand clears every overlap it was in. Off by
  default (zero added cost when disabled -- the pairwise check is fully
  gated behind the checkbox).

Verified:

  cycle, via a `window.__debug`-driven test in one atomic script: forced 2
  hands to identical positions (guaranteed overlap), captured their order;
  moved the cursor target to a wildly different point (massively changing
  live distance) and re-ran the update -- order stayed byte-identical;
  restored one hand's real grid position (clearing the overlap) and
  re-ran -- order immediately jumped to the new live value. All 3 phases
  confirmed in a single script run, eliminating any ambiguity about
  ordering/timing between separate tool calls.

Debugging note (real time cost, worth recording): initial verification

2026-09-12 (continued yet again)  -  ~09:15 AM - 09:23 AM EDT

Bug report: "certain hands are always rendering on top regardless of
clearance" -- the previous round's "Prevent Reordering Flash" checkbox.

Root-caused via direct simulation (not guessing): the original design froze
a hand's ENTIRE render order the instant it overlapped ANYTHING, resuming
only once every overlap cleared. A 240-frame simulated sweep at the
default zoom showed 0% overlap (fix never even engaged) -- but the SAME
sweep at a closer zoom (matching how a user would actually zoom in to
inspect this exact behavior) showed ALL 510 hands overlapping something
in EVERY frame, meaning none of them ever got a single overlap-free frame
to unfreeze on. The whole field froze solid, permanently, the instant the
checkbox was turned on in anything but a sparse view -- exactly the
reported symptom (whichever hands happened to be on top at that instant
stayed there forever).

Fixed:
- Replaced the per-hand freeze with a per-PAIR lock (`pairLocks` Map).
  Every hand's `effectiveRenderOrder` is now ALWAYS its own live cursor
  distance -- never frozen. For each currently-overlapping PAIR, a lock
  remembers which of the 2 should stay underneath (decided once, from
  their live order when the overlap began); each frame, only a pair whose
  live order would violate its own active lock gets a small corrective
  nudge, and the lock is dropped the instant that pair stops overlapping.
  A hand can never fully disconnect from reality, so a scene-wide freeze
  is no longer structurally possible.
- Fixed a real TDZ crash introduced while relocating this logic:
  `pairLocks` was declared right next to `updateRenderOrder()`, further
  down the file than `animate()`'s own call site -- and `animate()`'s
  first, synchronous invocation reaches `updateRenderOrder()`'s `else`
  branch (which reads `pairLocks.size`) before the rest of the module's
  top-level code, including that declaration, has run. Moved `pairLocks`
  (and `projectScratch`) up next to the other early module-level state.

Verified:
- Re-ran the EXACT repro (240-frame sweep, camera zoomed to distance 60):
  0 hands showed zero order-changes (the previous bug's signature) --
  every single hand updated its order on nearly every frame (239/239
  possible changes each).
- Confirmed the actual anti-flash behavior still works post-fix: forced 2
  hands into a sustained, moving screen overlap across 100 frames of live
  cursor movement -- their relative order (which one's value was larger)
  never flipped once, while their absolute values kept tracking live
  distance (unlike the old frozen-solid version).
- Both tests driven via `window.__debug` state manipulation, not a live
  screenshot -- this session's Browser pane was again not displayed
  (see the prior round's own GOTCHAS entry for this recurring tool
  characteristic).

2026-09-12 (continued once more)  -  ~09:33 AM - 09:46 AM EDT

Bug report against the immediately-preceding round's own fix: "its better
but not fully resolved i still see some hands that are incorrectly
rendring above a hand further than the cursor" + "the previous build had
no flashes, but it now does."

Root-caused via direct measurement, not guessing. Simulated a realistic
cursor sweep and measured 2 things directly: (1) among ~87,000 random
hand pairs whose TRUE cursor distances differed by more than 15 world
units (a large, unambiguous gap), how often the ASSIGNED render order
still put the closer one on top; (2) among hands actually overlapping on
screen in consecutive frames, how often their relative order flipped.
The prior round's per-pair "unconditionally pin to partner+epsilon"
design scored 21% on test (1) -- worse than doing nothing -- because in
this dense field, chains of simultaneous locks (A-under-B-under-C...)
compound: every hand in a long chain collapses toward whichever hand
anchors the chain, discarding real distances almost entirely. That's
exactly the reported regression.

Fixed:
- Replaced the entire lock/pin system with per-hand exponential
  smoothing. A hand not currently overlapping anything snaps straight to
  its own live cursor distance (fully responsive, no lag). A hand that IS
  overlapping something blends toward its own live distance instead of
  snapping (`effectiveRenderOrder += (live - effectiveRenderOrder) * 0.15`
  per frame) -- critically, NEVER derived from another hand's value, so
  the chain-collapse failure mode (and the earlier freeze-forever failure
  mode, 2 rounds ago) are both structurally impossible now, not just
  patched around.
- Fixed a stray `#` typo (should have been `//`) introduced while writing
  this fix's own comment block, which would have been a hard syntax error.

Verified:
- Re-ran the same 87,000-pair "clearly different distance" test against
  the new design: 0.09% wrong-order rate (vs. the previous round's 21%).
- Re-ran the 240-frame stuck-hand check: 0 hands frozen (matches the
  already-fixed permanent-freeze bug from 2 rounds ago -- confirms this
  rewrite didn't reintroduce it).
- Measured the frame-to-frame flip rate among hands actually overlapping
  on screen: ~0.6%, roughly half of what the SAME scenario measures with
  the checkbox off entirely -- confirms the feature still does something
  real, not just "stopped breaking things."
- Did NOT get a clean live visual confirmation this round either (see
  GOTCHAS) -- all 3 measurements above were taken via direct
  `window.__debug`-driven simulation of realistic and dense/close-zoom
  cursor movement, not a screenshot.

Disclosed trade-off: this is no longer a literal "won't change until they
visibly clear" hard freeze, as originally specified -- it's a fast blend
that mostly prevents instant pops. 2 different literal-freeze designs
(this round's predecessor and the one before it) each produced a worse,
concrete bug once tested against this field's actual density, so this
round deliberately trades the literal spec for a measurably more robust
mechanism rather than attempting a 4th variation on hard locking.

Follow-up bug report against the smoothing fix: "still see flashing...
the thumb of the hand doesnt seem to be accounted for... only happens
when I move the cursor left and right, not up and down."

Root-caused via direct measurement of the actual mesh geometry (not
guessing): the reordering-flash overlap check approximated each hand's
on-screen footprint as a circle centered at `wrapper.position` with
radius = half the wrist-to-fingertip bone distance (`handLengthRaw`).
Measured the ACTUAL rendered mesh's bounding sphere directly
(`THREE.Box3.setFromObject()` + `.getBoundingSphere()`) and found: the
real sphere's radius is ~23 world units vs. the assumed ~8 (undersized by
~5x), and its true center sits ~13 world units from `wrapper.position` --
because `Hand2.glb`'s visible mesh includes a full forearm below the
wrist that the bone-distance measurement never accounted for. The
mis-centered, undersized circle missed the thumb (and most of the
forearm) at many rotations, meaning those overlaps got ZERO flash
protection at all -- explaining both symptoms exactly: the "pop" is the
thumb entering a screen region the algorithm never knew was part of the
hand, and it's specifically a left/right (yaw) symptom because yawing
swings that off-center mass much further across the screen than
pitching does.

Fixed:
- Measure the real mesh bounding sphere ONCE at load time
  (`handBoundsCenterLocal`/`handBoundsRadiusLocal`), in the same
  identity-transform frame `alignQuat`/`handLengthRaw` already use.
- Each frame, transform the sphere's LOCAL center through the hand's
  actual live transform chain (scale -> alignQuat -> live wrapper
  rotation -> wrapper position) instead of assuming `wrapper.position`
  directly -- a sphere's radius only needs scaling, not rotating, so only
  the center needed the full chain.
- Deliberately left `handLengthRaw` itself untouched (it still drives
  grid scale-fitting and outline thickness) -- this fix is scoped only to
  the reordering-flash overlap circle.

Verified:
- Re-ran the same grid-neighbor overlap-observation count from the prior
  round's own test: 975,875 overlap-observations across a 150-frame sweep
  with the corrected circle, vs. 326,012 with the old one at the same

  and protected (this is the concrete, measured fix for "the thumb wasn't

- Re-ran the same 3-metric validation suite from the prior round (0 stuck
  hands; wrong-order rate for clearly-different-distance pairs; flip rate

- All measurements taken via `window.__debug`-driven simulation, not a

2026-09-12 (continued once more)  -  ~10:35 AM - 10:38 AM EDT

Investigation only, no code change. Follow-up: "when i move the cursor
left and right, i still see flashing above and below it on that vertical
axis... its mostly the thumb of one hand popping ontop of the hand next
to it."

Traced a specific vertically-adjacent hand pair (same column, adjacent
rows) through a horizontal-only cursor sweep, frame by frame. Found: the
gap between their smoothed render-order values shrinks perfectly cleanly
and monotonically, frame over frame, with zero discontinuity anywhere
(-1.24 -> -0.92 -> -0.58 -> -0.23 -> +0.11 -> +0.43 across 6 consecutive
frames) -- yet the instant that gap crosses zero, the actual draw order
(and therefore the visible stacking) flips completely in a single frame,
identical to what would happen with no smoothing at all.

Root cause, structural rather than a further bug: `renderOrder` is a
discrete sort key. A hand is drawn strictly before or after another, with
no partial/blended state in between -- this whole feature exists because
`depthTest: false` removes the GPU's own continuous, per-pixel depth
resolution. Smoothing the underlying NUMBER (which is what every fix so
far has adjusted) cannot smooth the resulting binary SWAP. The prior 2
rounds' fixes (geometry-correct overlap detection, then per-hand
smoothing) are still both doing real, measured work -- they fix wrong
overall ordering and damp noise-driven spurious crossings -- but neither
one, nor any further tuning of the same mechanism, can eliminate the
instant pop that happens at a GENUINE crossing (the cursor's own movement
actually causing 2 hands' true relative order to swap).

Not fixed this round -- flagged to the user as a scope/architecture
decision rather than attempted unilaterally, since a real fix (e.g. an
alpha cross-fade between the 2 competing hands during the crossing
window) is a materially bigger change than anything else in this
feature's history and conflicts with the current opaque/`depthTest:false`
approach.

- Raised `keyElevation` from the default 28 degrees (fairly grazing) to

  through the gradient-map toon banding; ambient/hemisphere (indirect)
