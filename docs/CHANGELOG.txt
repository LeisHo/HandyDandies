2026-09-12  -  ~06:54 AM - 07:22 AM EDT (bounded by checkpoints; see Verified note)

Initial build: a three.js scene filled with a grid of rigged hand instances
that each independently rotate to point at the live cursor. Built per
explicit instruction to follow HANDO's own hand-rendering architecture as
the reference.

Added:
- Reused HANDO's rigged hand asset (`data/HAND3D/HAND-021/Hand2.glb`,
  22-bone skeleton, GLB format), physically copied into this project's own
  `data/processed/HAND3D/Hand2.glb` (no cross-project asset serving).
- Reused HANDO's generic dev-panel engine (`src/devpanel/devPanel.js`) and
  its dev-panel CSS chrome (`src/style.css`) verbatim.
- New: cursor-to-3D-target math (HANDO itself has no cursor-tracking --
  it's a manual single-hand pose tool). Each frame, the cursor's screen
  position is raycast against a plane positioned in front of the hand
  field (toward the camera); each hand instance slerps its rotation toward
  a look-at quaternion aimed at that 3D point.
- New: per-instance skeleton cloning (`SkeletonUtils.clone()`) so each of
  the 54 (default 6x9 grid) hand instances can aim independently -- HANDO
  only ever renders one hand, so this had no precedent to follow.
- New: bind-pose "pointing direction" measurement (wrist bone `rHand` to
  fingertip bone `rMid3`, in world space at load time) rather than assuming
  a fixed axis -- matches HANDO's own "measured, not assumed" convention
  for this rig.
- Dev panel groups: Field Layout (rows/columns/spacing/hand scale), Cursor
  Tracking (damping, target depth, target-marker toggle), Camera (FOV,
  distance), Lighting (key light azimuth/elevation/intensity/color,
  ambient), Background, Debug (grid helper).

Fixed (both caught live during the build, before this entry):
- `three/addons/utils/SkeletonUtils.js` (three@0.169.0, the pinned CDN
  version) exports `clone`/`retarget`/`retargetClip` directly, not a
  `SkeletonUtils` namespace object -- confirmed by directly fetching and
  reading the served module source. `import { SkeletonUtils } from '...'`
  threw `SyntaxError: does not provide an export named 'SkeletonUtils'` at
  module-load time. Fixed via `import { clone as cloneSkeletal } from
  'three/addons/utils/SkeletonUtils.js'`.
- `initDevPanel()`'s synchronous onChange-on-restore behavior would throw a
  TDZ (temporal dead zone) error against `camera`/`keyLight`/etc. (declared
  later in the file, via `const`) the first time a returning visitor had
  saved settings. Fixed with the same detach-onChange-before-init/
  reattach-after mitigation HANDO's own `main.js` already uses for this
  exact documented gotcha.

Added:

- Row Spacing and Column Spacing as 2 independent sliders, replacing the
  single shared "Cell Spacing." Alternate Row Offset (brick/hex-style,
  every other row shifted along the column axis) and Progressive Row
  Offset (row `r` shifted by `r` times the setting) as 2 mutually-exclusive

- Full Lighting group parity with HANDO (added Key Light Aim Height). New

  N hand instances (one shared toon material; a per-instance hull-outline
  clone OR a single OutlinePass covering every instance's skinned mesh,
  toggleable).

Fixed:
- Field Layout previously called camera/lighting/target-plane framing
  functions on every rows/cols/spacing change, so changing the grid
  visibly rescaled the camera view -- explicitly not wanted ("Field
  layout shouldn't affect view scale"). Framing is now derived from the
  field's bounding size exactly ONCE (`framedOnce` flag in
  `rebuildField()`) and frozen after that; Field Layout changes only ever
  touch `relayoutField()` (positions/scale), never camera/light/
  target-plane again.
- `window.innerWidth`/`innerHeight` reading 0 at script-parse time in this
  dev environment left the renderer/`EffectComposer`/`OutlinePass`
  permanently zero-sized once post-processing was added (confirmed:
  `renderer.getSize()` reporting `[0,0]`, `GL_INVALID_FRAMEBUFFER_OPERATION:
  ...Attachment has zero size` spamming the console). Fixed with a
  per-frame self-healing size check in `animate()`, sharing one
  `applyRendererSize()` function with the `resize` event listener --
  same fix shape as a previously-documented DOTFLICKO gotcha for this
  exact class of quirk.

Verified:

  genuinely shift and scale on each gesture.
- Field-layout/camera decoupling, DIRECTLY (not just visually): dispatched

- Progressive Row Offset visually produces the expected cascading/

- Both outline techniques (hull-mesh clone and screen-space OutlinePass)

- Every new dev-panel group and control (Row/Column Spacing, Alternate/

  target line to a new distance (the same axis OrbitControls' own scroll/

- Cursor-distance render ordering: every frame, each hand's
  `skinnedMesh.renderOrder` is set to its own live distance from the
  cursor target (farther = higher = drawn later = ends up on top); its
  `outlineMesh.renderOrder` is that value minus a small epsilon so a
  hand's own outline always draws just under its own fill. Required
  `depthTest: false` on both hand materials (kept `depthWrite: true`) --
  three.js's normal depth-tested compositing otherwise always lets real
  camera depth win over renderOrder. Disclosed tradeoff: a single hand's
  own internal self-occlusion (finger over finger) now relies on
  front-face culling + triangle order, not a real per-pixel depth test --
  acceptable for this model's mostly-convex static bind pose.

2026-09-12 (continued yet again)  -  ~08:52 AM - 09:04 AM EDT

1 request: a "Reordering Flash" checkbox so 2 overlapping hands' cursor-
distance render order doesn't flip/flash while they're still overlapping,
only once they visibly clear each other.

Added:
- `preventReorderFlash` checkbox (Debug group). When on,
  `updateRenderOrder()` approximates every hand's on-screen footprint as a
  circle (world radius = half the measured hand length x its own scale,
  projected to screen pixels via standard perspective scaling) and runs an
  O(n^2) pairwise screen-space overlap check across all hands. A hand's
  `effectiveRenderOrder` (now a persisted field, not recomputed from
  scratch every frame) only updates from its live cursor-distance when it
  is NOT currently overlapping anything -- while overlapping, it keeps its
  prior order, so 2 fighting hands can't flip mid-overlap; it only
  re-evaluates once that hand clears every overlap it was in. Off by
  default (zero added cost when disabled -- the pairwise check is fully
  gated behind the checkbox).

Verified:
- The full freeze -> stay-frozen-despite-large-distance-change -> resume
  cycle, via a `window.__debug`-driven test in one atomic script: forced 2
  hands to identical positions (guaranteed overlap), captured their order;
  moved the cursor target to a wildly different point (massively changing
  live distance) and re-ran the update -- order stayed byte-identical;
  restored one hand's real grid position (clearing the overlap) and
  re-ran -- order immediately jumped to the new live value. All 3 phases
  confirmed in a single script run, eliminating any ambiguity about
  ordering/timing between separate tool calls.

Debugging note (real time cost, worth recording): initial verification
attempts showed the overlap check always reporting no-overlap and NaN-like
projected screen positions, which looked like a bug in the new code. Root
cause was NOT the new code: this session's Browser pane was not currently
displayed at all (confirmed via `tabs_context`: "The Browser pane is
currently hidden"), which fully suspends `requestAnimationFrame`
(confirmed with a vanilla rAF-counting script having nothing to do with
this project) -- and since the existing camera-resize self-heal fix (added
in an earlier round for the `window.innerWidth`-reads-0-at-boot issue)
lives inside the rAF loop, it never got a chance to run, leaving the
camera stuck with a NaN projection matrix (constructed with
`aspect = 0/0` at boot). Manually repairing the camera via a debug hook
(`camera.aspect = <real ratio>; camera.updateProjectionMatrix()`) before
re-testing resolved it completely -- the overlap-detection code itself was
correct the whole time. See CODE_SUMMARY.txt's GOTCHAS for the durable
writeup.
